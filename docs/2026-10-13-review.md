## 本轮审查发现并修复的最后一处问题

在检查生产入口时，发现 watchdog 原先只对 `0/64/130` 停止，其他退出码都可能进入恢复等待。这样，发生在正式工作循环之前的确定性异常，例如损坏的 readiness 记录造成 `KeyError`，仍可能以退出码 1 被不断重启。

提交 `7eec063` 将 watchdog 重试限定为显式基础设施退出码 **75**。其他退出码直接返回；入口层未预料异常保存 `controller_failures/*.json` 并以 64 停止；环境漂移和清理失败也不会被监控层改写成普通恢复。回归覆盖异常启动记录，以及 `0/1/64/130/-9` 均不进入恢复循环。这是第 3、4 条的错误分类修复，没有增加第 16 条所拒绝的全局重试预算。

## 冻结环境与运行边界

准备记录为 [runtime.json](../outputs/diagnostics/hybrid_runtime_20261013/runtime.json)，SHA-256 为 `50249d6a266b0929b2ad3884e8a8f388c754b39868c1707529840a03bc3bec2b`。机器可读计划同时固定路径和哈希；新 controller 会复制 Docker helper 源码和 seccomp 配置，运行时检查所用镜像与这些源码相符。

| 项目 | 已验证配置 |
| --- | --- |
| Docker 镜像 | `sha256:5166b66de4acb50df6c390d43858f4d946a8351d215006cbd5b2c0fac1901a0e`；本地标签 `decompbench-agents-v2:20261013` |
| CLI | Codex 0.162.1；Claude Code 2.1.296；AGY 1.3.1 |
| Docker engine | client/server 29.4.3；绑定本地 Unix endpoint 与 engine ID，不依赖之后可改变的默认 context |
| 求解器环境 | macOS arm64；Python 3.12.11；gurobipy/Gurobi 11.0.3；其余当前安装包版本归档于 manifest |
| 容器资源 | 每个编辑 worker 1 CPU、1,024 MiB、128 个 PID；只读 root、无宿主目录 bind mount、无额外 capabilities、私有 tmpfs 与临时工作卷 |
| 总体资源监测 | 原有 host CPU/RSS、系统内存及 thermal guard，加上带 V2 worker 标签的容器 CPU/RSS；不只统计宿主 Docker CLI 的轻量进程 |
| 本机进程限制 | 一个合成 Seatbelt profile；禁止 `setsid`、`setpgid`、`posix_spawn`，普通 Python fork/exec 子进程已验证；收集输出前停止并核对整个归属进程组 |

原拟在 `codex sandbox` 中再套一层 sandbox 的做法不适用：macOS 拒绝给同一进程再次套 sandbox。实现改为单次 `/usr/bin/sandbox-exec`，组合文件、网络和进程限制，并固定 launcher、系统 dyld profile 与实际 Python runtime 的哈希。直接执行 Homebrew 的实际 Python runtime，避免其外层 launcher 使用被禁止的 `posix_spawn`。这是有证据支持的实现调整；没有静默回退到不受限求解。

上述 subprocess 限制是新运行环境的实际约束，应随 cohort 保留。等价的 Python 调用路径拼写不会被误判为漂移，但解析后的 binary、package 路径、依赖版本及其他环境字段仍需相符。科学协议或实际环境需要改变时，应重新准备并审阅相应冻结证据。
